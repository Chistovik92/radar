# План версии 6.0.0 — большое обновление «Радар»

**Цель версии 6.0.0:** три крупных блока в одном выпуске — (1) лёгкий движок
управления контентом сайта (CMS), (2) музыка с поиском, прослушиванием и
соц.механикой, (3) отдельный бот тикет-поддержки, — плюс установщик, который
ставит **два бота** (основной «Радар» и поддержку) в разных Docker-контейнерах
одной командой.

Это смена состава системы (добавляется второй постоянный бот и публичный
музыкальный каталог), поэтому номер старший — **6.0.0**, а не 5.12.

Все три части подробно расписаны в своих документах; здесь — общая канва,
порядок и то, что объединяет их в один выпуск.

| Часть | Документ | Суть |
| --- | --- | --- |
| A. CMS | [PLAN_SITE_CMS.md](PLAN_SITE_CMS.md), разделы 1–6 | суперадминистратор правит тексты лендинга из веб-панели, без правки `.tsx` и пересборки |
| B. Музыка | [PLAN_SITE_CMS.md](PLAN_SITE_CMS.md), разделы 7–13 | поиск SoundCloud/YouTube, стриминг, избранное, история, публичный каталог (топ/плейлисты/шаринг/лайки) |
| C. Поддержка | [PLAN_SUPPORT.md](PLAN_SUPPORT.md) | отдельный бот тикетов: номера `#год-N`, закрытый доступ, SLA, экспорт диалога |
| D. Установщик | этот документ, раздел 4 | `install.sh` ставит оба бота в разных Docker'ах |

---

## 1. Почему одним выпуском

- **CMS и музыка** завязаны на одни и те же `meta`-кэши и правила работы с
  `storage`/`meta` (merge-логика из Части A переиспользуется в музыке).
- **Музыка и поддержка** — два новых «лица» бота наружу; оба требуют аккуратной
  оговорки в правилах/политике (наши тексты Privacy/Terms, а не чужие).
- **Установщик двух ботов** — сквозная тема: без него поддержка не существует
  как продукт. Делается в этом же выпуске, чтобы «поставил — и работает».

Порядок реализации внутри выпуска — по зависимостям (см. раздел 5), а не по
нумерации частей.

---

## 2. Часть A — CMS (кратко)

Полное описание — `PLAN_SITE_CMS.md`, разделы 1–6.

- Хранилище контента — `meta` (JSON), ключ на секцию; суперадминистратор
  правит текст/списки через панель, без пересборки бандла.
- Структура/макет не редактируются — движок управляет содержимым, а не вёрсткой.
- Privacy/Terms остаются серверно-рендеренными (`radar/web/public_pages.py`)
  ради платёжной системы Platega (требование совместимости).

## 3. Часть B — Музыка (кратко)

Полное описание — `PLAN_SITE_CMS.md`, разделы 7–13. Перенос из
[`not_a_music`](https://github.com/pythoneer-dev-q/not_a_music):

- **Движок** `radar/musicsearch.py` — порт `core/app_logic.py` (SoundCloud
  api-v2 + резерв YouTube на yt-dlp, выбор битрейта, прогресс-бар). Сеть +
  yt-dlp, от БД не зависит — переносится почти как есть.
- **Слой данных** — на наш SQLite/`meta`, без MongoDB (`motor`/`pymongo`/
  `nanoid` не тянем; короткие id — `secrets.token_hex`).
- **Соц.механика внедряется полностью** (решение владельца): публичные
  плейлисты, топ треков/плейлистов, шаринг, лайки/дизлайки, профиль-статистика.
  Оговорка из шапки `radar/music.py` («каждый слушает только своё») остаётся
  верной для «Мои треки»; публичный каталог — отдельный флаг `music_search`.
- **Правила/политика — наши** (`landing/src/pages/Privacy.tsx`, `Terms.tsx`,
  серверный рендер в `public_pages.py`), не из `not_a_music`.

## 4. Часть C — Поддержка (кратко)

Полное описание — `PLAN_SUPPORT.md`. Отдельный лёгкий бот в том же репозитории
(`support/`), без Gemini/yt-dlp/ffmpeg в обязательном наборе.

- **Тикеты** с порядковым номером `#год-N`; закрытый доступ: только автор ИЛИ
  роль модератор+; весь диалог — внутри тикета.
- **FAQ + ИИ-ассистент** (Gemini, флаг `support_ai`), **SLA полностью**,
  **вложения** принимаются, **оценка 👍/👎** по закрытию.
- **Группа с топиками**: бот добавлен в группу, где уже есть основной «Радар»;
  одна тема = один тикет.
- **Экспорт** диалога текстовым `.txt` — по запросу и по закрытию.

## 5. Порядок реализации

1. **Движок поиска музыки** `radar/musicsearch.py` + офлайн-тесты (перенос
   `core/app_logic.py` без сети). Самый независимый кусок.
2. **Слой кэша `meta`** (`music_catalog`, `music_files`) + merge-тесты — общий
   с CMS-движком.
3. **Обработчики музыки**: поиск → воспроизведение → `file_id`-кэш; избранное,
   история, недавние, профиль-статистика.
4. **Соц.механика** `radar/music_social.py` + обработчики: публичные плейлисты,
   лайки/дизлайки, просмотры, топ, случайный, шаринг.
5. **Инлайн-режим и шаринг** через инлайн-кнопки.
6. **CMS-движок** (Часть A): правка текстов лендинга через панель, `meta`-слой,
   лимиты, server-render Privacy/Terms.
7. **Бот поддержки** `support/`: модели, движок, обработчики (личка + группа),
   SLA, экспорт, FAQ + ИИ.
8. **Установщик двух ботов** (раздел 6): `install.sh` + второй контейнер,
   `SUPPORT_*` переменные, вопрос о токене поддержки.
9. **Флаги и документация**: `music_search`, `support_ai`; i18n; README,
   MANUAL, STATUS, ROADMAP; релиз-запись 6.0.0.
10. **End-to-end** на сервере: поиск→прослушивание→повторно мгновенно;
    публичный плейлист и шаринг в чужой чат; тикет от создания до экспорта;
    установка двух ботов с нуля.

## 6. Установщик: два бота в разных Docker

Сейчас `install.sh` ставит один бот (`radar_container`, образ `radar_image`)
в каталог `~/radar_bot`. Для 6.0.0 установщик опционально ставит **второго
бота — поддержку** — отдельным контейнером.

### 6.1 Что меняется в `install.sh`

- Новый шаг-вопрос: «Поставить бота поддержки?» (да/нет, по умолчанию нет).
- При «да» запрашивается токен поддержки (отдельный от основного; если токен
  совпал с основным — предупреждение и повторный запрос).
- Заполняются `SUPPORT_*` в `.env`:
  - `SUPPORT_BOT_TOKEN` — токен бота поддержки;
  - `SUPPORT_ADMIN_ID` — Telegram ID администратора поддержки (обычно тот же
    `SUPERADMIN_ID`, но можно отдельный);
  - `SUPPORT_DB_FILE=data/support.db` — своя база;
  - `SUPPORT_GROUP_ID` — id группы с топиками (необязательно на старте).
- Сборка и запуск второго контейнера с уникальными `container_name` /
  `image`: `support_container` / `support_image`.

### 6.2 Разведение по портам и данным

| Параметр | Основной «Радар» | Поддержка |
| --- | --- | --- |
| токен | `BOT_TOKEN` | `SUPPORT_BOT_TOKEN` (другой) |
| БД | `DB_FILE=data/radar.db` | `SUPPORT_DB_FILE=data/support.db` |
| контейнер | `radar_container` | `support_container` |
| образ | `radar_image` | `support_image` |
| веб-панель | `WEB_PORT=8080` | не нужна (поддержка без панели) |

### 6.3 Обновление и диагностика

- `doctor.py` проверяет оба контейнера (два токена, две базы, порты не
  пересекаются).
- Обновление (`--version`, обновление из панели) пересобирает оба образа;
  сбой поддержки не роняет основной бот (отдельный проект/контейнер).
- `tools/uninstall.sh` чистит оба контейнера и оба `SUPPORT_*` ключа.
