# План: движок управления контентом сайта (CMS) и музыка для «Радар»

**Часть A — CMS.** Дать суперадминистратору редактировать тексты всех страниц
лендинга через интерфейс веб-панели, без правки `.tsx` и без пересборки
бандла. Контент хранится в базе данных.

**Часть B — Музыка.** Перенести в «Радар» функционал поиска и прослушивания
музыки из проекта [`not_a_music`](https://github.com/pythoneer-dev-q/not_a_music)
(поиск SoundCloud + резерв YouTube, стриминг, избранное, история, профиль,
шаринг, инлайн-режим), адаптировав его под наше хранилище (SQLite, запись
пользователя) и наш стек (aiogram 3 + aiohttp + yt-dlp). Правила и политику
конфиденциальности — использовать наши, не из `not_a_music`.

**Ограничение:** выход в панель — только у суперадминистратора (`@owner_only`).

## 0. Как читать этот документ

- Разделы **1–6** — исходный план CMS (Часть A). Без изменений.
- Разделы **7+** — Часть B, музыка по мотивам `not_a_music`. Добавлены этим
  обновлением. Нумерация продолжает исходную, чтобы ссылки из дорожной карты
  и истории не рвались.

## 1. Что меняем и почему (текущее состояние)

Сейчас лендинг — статический React SPA. Весь текст страниц зашит в JSX:

| Страница | Файл | Что зашито |
| --- | --- | --- |
| Главная | `landing/src/App.tsx` | заголовки, описания, возможности |
| Тарифы | `landing/src/pages/Pricing.tsx` | цены, тексты карточек |
| Политика | `landing/src/pages/Privacy.tsx` | весь текст документа |
| Соглашение | `landing/src/pages/Terms.tsx` | весь текст документа |
| Поддержка | `landing/src/pages/Support.tsx` | каналы, SLA, FAQ |
| Загрузки | `landing/src/pages/Downloads.tsx` | платформы, тарифы VPN |
| Проекты | `landing/src/pages/Projects.tsx` | список проектов |

Чтобы поменять одну строку, надо править `.tsx`, пересобирать `npm run build`,
пересобирать `install.sh` и выпускать релиз. Цель — убрать эту зависимость для
**текстового контента** (структура и стили остаются в коде).

**Уже есть фундамент:**
- `render_landing_page()` в `radar/web/landing.py` вшивает JSON в
  `<script id="radar-config">` — сюда можно добавить контент.
- Модель `Meta` (JSON key-value) + `storage.meta_get/meta_set` +
  `repo.get_meta/set_meta` — готовое хранилище в БД, **новая таблица не нужна**.
- Роль `superadmin` + декоратор `@owner_only` — готовый «выход только для
  суперадминистратора».
- Панель рендерит HTML на сервере (`_layout` + `section_body` + `_card_html`),
  формы через `_guarded_form` с CSRF-токеном.

## 2. Ключевые проектные решения

### 2.1 Хранение — в `meta` (без новой таблицы)
Контент каждой страницы — один словарь, сохранённый в `meta` под ключом
`"landing_content"`. Внутри — по ключу маршрута:

```json
{
  "landing_content": {
    "pricing":  { "intro": "...", "cards": [...] },
    "privacy":  { "sections": [ { "h2": "...", "body": "..." } ] },
    "downloads": { ... },
    ...
  }
}
```

Почему `meta`, а не отдельная таблица:
- модель уже есть, миграцию писать не нужно;
- JSON гибок — структуру страницы можно менять без `ALTER TABLE`;
- паттерн уже используется (`vpnsales` хранит заказы в `meta`).

**Следствие:** каждая страница получает **схему контента** (что за поля, их
типы и значения по умолчанию), описанную в коде. БД хранит только то, что
человек реально переопределил; если в `meta` нет записи — рендерится значение
по умолчанию (тот самый текст, что сейчас зашит в `.tsx`).

### 2.2 «Значения по умолчанию» — исходник правды
Текущие тексты из `.tsx` переезжают в один модуль-схему (например,
`radar/web/landing_content.py`) как значения по умолчанию. Это даёт:
- лендинг работает сразу, даже если в БД ничего нет;
- кнопка «Сбросить к значению по умолчанию» на каждый блок;
- откат легко: удалить запись из `meta`.

### 2.3 Передача в SPA — через существующий `radar-config`
`render_landing_page()` уже вшивает `payload` в `<script id="radar-config">`.
Добавляем туда поле `content`, собранное из `meta` + схемы по умолчанию.
React-страницы читают `readConfig()` (уже есть в `App.tsx`) и берут тексты
из `config.content` вместо зашитых строк.

### 2.4 Редактор — серверная страница панели (не React)
Редактор живёт в панели, в том же стиле, что «Настройки» (`settingspages.py`):
- новый раздел «Сайт» в `_nav_groups` (только для `owner`);
- страница `/site` — список страниц, `/site/{page}` — форма редактирования
  полей этой страницы;
- каждая форма — `<textarea>`/`<input>` для полей схемы, сохранение через
  POST в `meta`, CSRF через существующий `_guarded_form`.

Почему серверный рендер, а не React: панель уже целиком серверная, редактор
не должен зависеть от пересборки лендинга, и суперадминистратор редактирует
текст, а не интерактив.

## 5. Открытые вопросы (решить до/во время реализации)

1. **Markdown или plain text?** Для Privacy/Terms нужен многоабзацный текст
   со списками и заголовками. Вариант — хранить как markdown и рендерить на
   клиенте (добавить маленький markdown-рендерер в SPA) либо хранить как
   список секций `[{h2, body}]` (проще, но менее гибко). Рекомендую список
   секций — без новой зависимости и без XSS-риска от произвольного HTML.

2. **XSS / безопасность.** Контент рендерится React'ом как текст (не
   `dangerouslySetInnerHTML`), поэтому HTML из текста не исполнится. Это
   важно подтвердить для markdown-варианта, если выберем его.

3. **Privacy/Terms — статичность для платёжной системы.** Platega требует
   доступные тексты документов. При редактировании через БД тексты остаются
   в `radar-config` (JS). Если платёжной системе нужен статичный HTML без JS —
   решить, оставить ли Privacy/Terms серверно-рендеренными (через
   `public_pages.py`, который уже существует) или смириться с JS-рендером.
   Рекомендация: Privacy/Terms оставить на серверном рендере с чтением из
   `meta`, остальные — на SPA.

4. **Структура vs текст.** План правит только текст и простые списки
   (карточки проектов/платформ/тарифов). Перестройка вёрстки (колонки,
   порядок блоков) остаётся в коде. Это осознанное ограничение — движок
   управляет содержимым, а не макетом.

5. **Размер текстов.** Задать разумные лимиты длины полей (например, 10 000
   символов на секцию), чтобы не забить `meta` произвольными данными.

# Часть B — Музыка (поиск, прослушивание и соц.механика, по мотивам not_a_music)

## 7. Что переносим и почему

### 7.1 Исходник — `not_a_music`

[`pythoneer-dev-q/not_a_music`](https://github.com/pythoneer-dev-q/not_a_music) —
отдельный Telegram-бот (aiogram 3, aiohttp, motor/pymongo, yt-dlp, Apache-2.0),
который ищет музыку в SoundCloud, а если трек защищён (SoundCloud Go+/DRM) —
подбирает полноценную версию на YouTube, скачивает лучшую по битрейту дорожку
и отдаёт её в Telegram.

Полный набор возможностей (по `README` и коду):

| Группа | Что умеет |
| --- | --- |
| Поиск | SoundCloud постранично; премиум-треки Go+ отсеиваются; резерв YouTube, когда SC не отдаёт целиком |
| Прослушивание | стриминг/скачивание, выбор лучшего битрейта (SC `hls_aac_160k`, YouTube `140`=128 кбит/с), прогресс-бар |
| Избранное | ⭐️ прямо в выдаче; пагинация; лимит `USER_SAVED_LIMIT` |
| Плейлисты | ➕ из выдачи; лимиты `TRACKS_MAX`/`PLAYLISTS_MAX`; публичные плейлисты с просмотрами/лайками |
| История | 🕘 последние прослушивания, хранение 30 дней, удаление отдельного трека и очистка |
| Недавние запросы | 🔁 на экране поиска, до 5 штук |
| Топ | 🏆 топ треков по прослушиваниям; 🏆 топ публичных плейлистов; 🎲 случайный трек |
| Шаринг | ✈️ кнопкой под треком, инлайн-режим |
| Профиль | язык ru/en, видимость (скрытие), «О себе», статистика (прослушано/лайки/избранное/плейлисты) |
| Помощь | раздел «ℹ️ Помощь» с правилами и политикой конфиденциальности прямо в боте |
| Инлайн | поиск музыки в любом чате (`@bot запрос`) |

### 7.2 Что уже есть у нас (не дублировать)

Музыка в «Радаре» есть с 4.9.5, но устроена иначе — **только свои файлы**:

- `radar/music.py` — хранилище треков в записи пользователя
  (`user["music"]`: `tracks` + `playlists`), ID3-разбор, лимиты, подбор похожего
  по тегам, подборки по жанру/артисту, пережатие в opus, кэш/облако;
- `radar/handlers/music.py` — приём `F.audio`, команда `/music`, плейлисты,
  воспроизведение `answer_audio`, пережатие, перемешивание;
- `radar/musicmeta.py` — дополнение метаданных из открытых баз (MusicBrainz),
  флаг `music_meta`;
- `radar/cloudstore.py` + флаг `music_cloud` — вынос файлов в облако (rclone);
- `radar/discordmusic.py` + флаг `discord_music` — музыка по ссылке в Discord.

**Чего у нас НЕТ** (это и даёт `not_a_music`): поиск по внешнему каталогу
(SoundCloud/YouTube) и прослушивание чужого трека онлайн, избранное, история
прослушиваний, профиль со статистикой, топ, шаринг, инлайн-поиск. Всё это
переносим, включая соц.механику (публичные плейлисты, топ, шаринг, лайки) —
решение владельца, см. 9.4. Существующий раздел «Мои треки» (свои файлы)
остаётся как есть и сосуществует с новым публичным каталогом.

### 7.3 Ключевые различия, которые диктуют адаптацию

| Ось | `not_a_music` | «Радар» (наша цель) |
| --- | --- | --- |
| Хранилище | MongoDB (motor/pymongo), отдельные коллекции `m_search`, `m_db`, `m_pllist`, `m_users`, `m_nav`, `m_likes`, … | SQLite/PostgreSQL через SQLAlchemy; состояние — в записи пользователя и в `meta` (JSON), как у существующей музыки |
| Модель доступа | публичный каталог: топ, публичные плейлисты, шаринг, лайки/дизлайки | **публичный каталог внедряем полностью** (топ, публичные плейлисты, шаринг, лайки/дизлайки) — решение владельца, см. 9.4 |
| Настройки | `m_settings` (коллекция) + `.env` (`Config`) | наша система флагов `features` + настройки панели |
| Языки | i18n ru/en в `utils/i18n.py` | наша `radar/i18n.py` (+fa/uk/zh), тексты через `_()` |
| Навигация | callback-payload в `m_nav` (TTL 7 дней), `m_state.last_cb` | наш `states.Form` (aiogram FSM) + inline-кнопки |

Вывод: **движок поиска/скачивания (`core/app_logic.py`) переносится почти как
есть** (это чистый yt-dlp + aiohttp, от БД не зависит), а **слой данных и
обработчиков переписывается под наш SQLite и наши соглашения.**

## 8. Что именно переносим из кода (по файлам)

### 8.1 Берём почти без изменений — `core/app_logic.py`

Это сердце `not_a_music`: гибридный клиент SoundCloud+YouTube на yt-dlp.
Содержит (по функциям/классам):

- `ytdl_env_opts()` — настройки yt-dlp из окружения (`YTDLP_COOKIES`,
  `YTDLP_PLAYER_CLIENT`, `YTDLP_PROXY`, `YTDLP_JS_RUNTIMES`); совпадает с нашими
  `YTDLP_*`/`COOKIES` механизмами — сверить имена переменных;
- `_pick_best_audio()` — выбор лучшего аудио-формата (сортировка по битрейту,
  отсев DRM/видео/preview, поддержка HLS для SC);
- `score_candidate()` + `_BAD_VERSION_WORDS` — оценка кандидатов YouTube по
  длительности и словам, штраф за «slowed/remix/cover/…»;
- `format_progress_bar()` / `TelegramProgressReporter` — прогресс-бар загрузки;
- SoundCloud api-v2: `_load_client_id()`, `fetch_track_states()`,
  `get_track_states()` (кэш), `is_premium_track()`, `_is_playable_transcoding()`;
- `search_via_api()` — независимый поиск через api-v2; предохранитель
  `_api_health_*` (после 3 сбоев api-v2 отключается на 120 с);
- класс `MusicClient`: `search_track()` (двухстратегийный поиск SC + добивка
  YouTube), `_drop_premium()`, `top_tracks()`, `get_track_info()`,
  `_find_youtube()`, `download_track()`, `_download_with_ytdlp()`,
  `_download_bytes()` (Range-чанки с повторами и проверкой полноты).

Всё это — сеть и yt-dlp, **без единого обращения к MongoDB** (кроме
`MusicClient._stored_meta`, который ходит в `music_db` — его переписать под наш
слой, см. 8.3). Дополнительных зависимостей не тянет: `aiohttp`, `yt-dlp`,
`asyncio` у нас уже есть.

### 8.2 Переписываем под наш стек — слой БД

Аналог `database/*.py` из `not_a_music`, но на нашей SQLAlchemy/SQLite:

| Из `not_a_music` | Куда у нас / как |
| --- | --- |
| `m_users` (профиль, `played_count`, `lang`, `is_hidden`, `about`) | запись пользователя (у нас уже есть роль/язык/настройки). Поля `about`, `played_count`, `is_hidden` — добавить в слот музыки или в запись |
| `m_search` (кэш метаданных найденных треков) | `meta` (JSON) — глобальный кэш «трек → artist/title/duration/cover/url», аналогично `vpnsales` |
| `m_db` (скачанные треки: `file_id` в Telegram) | слот `user["music"]` + `meta` для глобального кэша file_id по track_id |
| `m_pllist` (публичные плейлисты) | `meta` (JSON): публичные плейлисты с просмотрами/лайками/шарингом — внедряем (решение 9.4) |
| `m_likes`/`m_dislikes`/`m_views`/`m_saved` | `meta` (JSON) или отдельные слоты; лайки/топ/избранное — внедряем |
| `m_nav` (payload-навигация) / `m_state.last_cb` | **не нужен**: у нас aiogram FSM (`states.Form`) и inline-кнопки; payload-индирекция не требуется |
| `m_settings` + `Config` | наша система `features` (флаги) + настройки панели; лимиты (`USER_SAVED_LIMIT` и т.д.) — константы модуля музыки |

### 8.3 Переписываем обработчики

Аналог `handlers/*.py`, но в стиле `radar/handlers/music.py` (Router + F.data +
`states.Form` + `textutils.esc`):

- `handlers.py` — меню, поиск текстом, создание плейлиста, «О себе»;
- `inline_handlers.py` — инлайн-поиск (`@bot запрос`), шаринг трека/плейлиста,
  кнопка `in_dl_` с докачкой через `downloader.download_track`;
- `service_handlers.py`, `admin.py` — служебные/админ-команды (перенести только
  то, что нужно: правила/помощь; блокировки/реклама/каналы — вероятно НЕТ,
  у нас своя модерация).

Тексты — через нашу `i18n` (`_()`), не копировать `utils/i18n.py`/`messages.py`
как есть: подставить наши ключи и переводы ru/en (+fa/uk/zh при наличии).

### 8.4 Правила и политика конфиденциальности — НАШИ

В `not_a_music` «ℹ️ Помощь» ссылается на свои правила/политику. **Их не берём.**
Вместо этого:

- тексты документов — наши: `landing/src/pages/Privacy.tsx` (политика) и

## 9. Архитектурные решения

### 9.1 Хранение найденных/скачанных треков

- **Кэш метаданных каталога** (`m_search` → `meta`): глобальный JSON-словарь
  `music_catalog`, ключ — `track_id` (SC id или `yt_<id>`), значение — плоская
  запись `{title, artist, duration, cover, url, query_str}`. Нужен, чтобы при
  недоступности SoundCloud всё ещё отдавать скачанные ранее треки и метаданные.
- **Скачанный аудио** — `file_id` Telegram: отдали трек один раз → сохранили
  `file_id` в `meta` (`music_files`) → в следующий раз отдаём мгновенно без
  повторного скачивания (ровно как `not_a_music` хранит `file` в `m_db`).
- **Избранное** — слот в записи пользователя (`user["music"]["saved"]`),
  лимит `FREE/SUBSCRIBED` по аналогии с треками.

### 9.1.1 Соц.механика (публичный каталог) — где хранится

| Сущность `not_a_music` | Куда у нас (`meta` / слот) |
| --- | --- |
| Публичный плейлист (`m_pllist`) | `meta["music_playlists"]`: `{short_id: {name, founder_id, tracks:[track_id], liked_by:[uid], views, likes, is_public}}` |
| Лайки/дизлайки трека (`m_likes`/`m_dislikes`) | `meta["music_likes"]`/`meta["music_dislikes"]`: счётчики + множества `uid` по `track_id` |
| Просмотры/прослушивания (`m_views`) | `meta["music_views"]`: счётчик по `track_id` (и плейлисту) |
| Топ треков/плейлистов | вычисляется из `music_views` / `music_playlists` сортировкой, без отдельного хранилища |
| История прослушиваний (`m_history`, TTL 30 дней) | слот `user["music"]["history"]`: список `{track_id, at}`; чистка при чтении/по расписанию |
| Недавние запросы (`m_state.recent_queries`) | слот `user["music"]["recent"]`, до 5 |
| Профиль-статистика (`played_count`, лайки) | слот/поля записи пользователя; лайки — сумма по `music_likes` |

Короткие публичные id (`short_id`) — наш `secrets.token_hex(8)` вместо `nanoid`.
TTL истории (30 дней) — приложение вычищает само (у нас нет Mongo-TTL): при
каждом чтении истории отбрасывать записи старше 30 дней.

### 9.2 Движок поиска — асинхронный, в executor

`yt-dlp` синхронный; в `not_a_music` вызовы обёрнуты в
`loop.run_in_executor(None, ...)`. Переносим так же, чтобы не блокировать
event loop оповещений (у нас мониторинг — приоритет). Прогресс — через
`TelegramProgressReporter` с `safe_edit` (наш аналог `edit_or_resend`).

### 9.3 Флаг включения

Отдельный флаг `music_search` (по умолчанию выключен), как принято у нас:
поиск по внешнему каталогу — это новый, потенциально рискованный для домена/
хостинга функционал (см. 9.4). Существующие `music` / `music_meta` /
`music_cloud` / `discord_music` не трогаем — поиск живёт рядом. Соц.механика
включается тем же флагом `music_search` (единый публичный каталог).

### 9.4 Соц.механика и юридическая оговорка

**Решение владельца (зафиксировано):** соц.механику внедряем **полностью** —
публичные плейлисты, топ треков и топ плейлистов, шаринг трека/плейлиста,
лайки/дизлайки, профиль со статистикой (прослушано/лайки/избранное/плейлисты).
Это осознанно расширяет текущую модель «каждый слушает только своё» до
публичного каталога.

Что это означает и как снимаем риски:

- **Треки не раздаём со своей стороны постоянно.** Скачанный трек отдаётся
  пользователю как `file_id` Telegram (отдали и забыли); в `meta` хранится
  только `file_id` + метаданные (artist/title/cover/url), а не сам аудиофайл.
  Это ровно то, что делает `not_a_music` (`m_db.file` = `file_id`).
- **Публичные плейлисты** — это ссылки на `track_id` и метаданные, а не сами
  файлы; воспроизведение идёт через тот же поиск/скачивание по `track_id`.
- **Топ** строится по счётчикам прослушиваний/лайков (`m_views`, `m_likes` →
  `meta`), не по содержимому фонограмм.
- **Шаринг** отдаёт в чужой чат метаданные и кнопку «скачать», а не аудиофайл
  напрямую (инлайн-режим `not_a_music`).
- **Источники — только бесплатные.** Отсев премиум SoundCloud Go+/DRM и
  защищённых площадок (Spotify/Apple/…) остаётся, как в `not_a_music` и в нашем
  `discordmusic.py`. Проигрывание с YouTube нарушает его условия — это уже
  явно прописано в наших релизах, оговорку сохраняем.
- **Оговорку в шапке `radar/music.py`** («каждый слушает только своё»)
  обновить: она остаётся верной для раздела «Мои треки» (свои загруженные
  файлы), а поиск/каталог описывает отдельный флаг `music_search` со своей
  оговоркой.

## 13. Что НЕ входит в Часть B (осознанно)

- MongoDB: не тащим motor/pymongo — всё на SQLite/`meta`.
- Система рекламы (`m_ads`), пригласительные каналы (`m_channels`), блокировки

- Отдельный systemd-сервис/`deploy.sh`/`docker-compose` бота — мы встраиваем
  в существующую установку «Радара».

  новых языков ради музыки.

сознательно — это решение владельца (см. 9.4), а не исключение.
