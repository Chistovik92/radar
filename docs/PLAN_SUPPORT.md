# План: движок тикет-поддержки «Радар» (отдельный бот)

**Цель:** отдельный минимальный Telegram-бот под Docker, который работает как
система тикетов поддержки. Клиент открывает обращение, получает порядковый
номер, ведёт диалог в рамках этого тикета; доступ к тикету — только у автора
и сотрудников администрации с ролью **модератор и выше**. По итогу диалог
сохраняется текстовым файлом.

**Отдельный движок, а не модуль «Радара»:** логика тикетов (номера, закрытый
доступ, статусы, SLA, экспорт диалога) в основном боте-мониторинге отсутствует.
Выносим в самостоятельный лёгкий бот. ИИ-ассистент (Gemini) — опционально за
флагом `support_ai`; yt-dlp и ffmpeg не тянутся вовсе.

---

## 1. Архитектура в целом

Три компонента (как в классической связке бот + движок + тикет-система),
но реализованные в одном процессе для простоты развёртывания:

| Слой | Роль | Где живёт |
| --- | --- | --- |
| Канал связи | Telegram-бот (токен из BotFather), точка входа | aiogram 3 long-polling |
| Движок обработки | парсинг, классификация, FAQ/база знаний, авто-ответ | `core/` |
| Тикет-система | хранение обращений, номера, статусы, SLA, экспорт | SQLite (SQLAlchemy) |

Бот работает в личных чатах (`/support` → новый тикет) **и в группе с топиками**,
куда добавлен основной бот «Радара» (решение владельца): одна тема = один тикет,
сообщение в топике создаёт тикет так же, как в личке.

### Стек

- Python 3.11+, **aiogram 3** + **aiohttp** (совпадает с «Радаром»);
- **SQLAlchemy[asyncio] + aiosqlite** (SQLite, файл рядом с ботом);
- `python-dotenv` (`.env`), без MongoDB, без yt-dlp, без ffmpeg; ИИ (Gemini) —
  опционально, через тот же подход `radar/ai.py`, за флагом `support_ai`;
- Docker: один контейнер, `restart: unless-stopped`, `.env` смонтирован.

Переиспользуем паттерны «Радара»: роли-иерархию (`radar/roles.py`), i18n-подход
(`radar/i18n.py`), модель `Meta` (JSON key-value) и запись пользователя — как
образцы. Живёт в том же репозитории `radar` (решение владельца): общий
`install.sh`, отдельный Docker-контейнер и отдельный каталог бота-поддержки.

## 2. Роли и права доступа

Наследуем иерархию: `user < moderator < admin < superadmin`.

| Роль | Что может в тикетах |
| --- | --- |
| `user` (клиент) | создать тикет, писать в **свой** тикет, читать только свои тикеты |
| `moderator`+ | видеть список всех тикетов, отвечать в любой, менять статус/приоритет, закрывать, экспортировать |
| `admin` / `superadmin` | то же + назначать роли, чистить/удалять тикеты |

Ключевое правило доступа (проверяется на каждый вход в тикет):
**автор тикета ИЛИ `roles.at_least(role, "moderator")`** — больше никто.
Обычный пользователь не видит чужие тикеты ни по номеру, ни по подбору.

`SUPERADMIN_ID` задаётся в `.env`; модераторы/админы назначаются внутри бота
командой (как в «Радаре» — `roles.assignable_roles`).

## 3. Модель данных (SQLite)

Таблицы (SQLAlchemy, стиль `radar/db/models.py`):

### 3.1 `users`
```text
id (PK), external_id (telegram id), username, role, lang,
created_at, blocked
```

### 3.2 `tickets`
```text
id (PK, autoincrement)            — он же порядковый номер тикета (см. 3.4)
author_id (FK users)              — кто открыл
status        : open | answered | closed
priority      : low | normal | high
subject       : краткая тема (первые слова первого сообщения)
category      : тема-классификация (см. 5), пусто — не определена
assignee_id   : оператор (FK users, nullable)
sla_due_at    : дедлайн первого ответа
created_at, updated_at, closed_at
```

### 3.3 `ticket_messages`
```text
id (PK)
ticket_id (FK tickets)
sender_id (FK users)              — кто написал (клиент или оператор)
kind      : text | system | attachment
body      : текст (или ссылка/описание вложения)
created_at
```

### 3.4 Порядковый номер

Номер тикета = `tickets.id` (автоинкремент). Человеку показываем его как
**`#2026-123`** — с префиксом года и порядковым номером (решение владельца).
Номер **не переиспользуется**: удаление тикета не освобождает номер.

## 4. Сценарий обращения

1. **Клиент жмёт «Поддержка»** (кнопка `/start`-меню или команда `/support`).
   Бот создаёт тикет, присваивает номер, отвечает:
   `Обращение #2026-123 создано. Опишите вопрос — ответим в этом диалоге.`
2. **Клиент пишет** — сообщения попадают в `ticket_messages` этого тикета.
3. **Оператор** (модератор+) видит тикет в очереди (`/queue` или кнопки),
   открывает по номеру, видит весь контекст, отвечает. Его ответ уходит
   клиенту и пишется в тот же тикет.
4. **Вся переписка — в рамках одного тикета**: смена оператора не теряет
   историю (она в `ticket_messages`).
5. **Закрытие.** Оператор (или клиент) закрывает тикет. Клиент оценивает ответ
   кнопкой 👍/👎 (решение владельца) — оценка идёт в статистику удовлетворённости.
6. **Экспорт.** По закрытию (или в любой момент оператору) формируется
   текстовый файл диалога (см. 7).

### Доступ «комната»

Тикет — закрытая комната: вход только автору и ролям модератор+. Проверка на
каждом сообщении/чтении по правилу из раздела 2. Попытка доступа к чужому
номеру от обычного пользователя — «Тикет не найден» (не раскрываем, что он
существует).

## 5. Движок обработки (FAQ + ИИ)

Решения владельца: **ИИ-ассистент нужен** (п. 4), **SLA — полностью сразу**
(п. 5), **вложения принимаются** (п. 6).

- **База знаний (FAQ)** — словарь «ключевые слова → готовый ответ» в `meta`
  (JSON), редактируется оператором. Если вопрос типовой — бот отвечает сразу
  и предлагает «создать тикет, если не помогло».
- **Классификация** — по ключевым словам и через ИИ проставляется `category`
  (например: «оплата», «доступ», «VPN», «прочее») для маршрутизации/статистики.
- **ИИ-ассистент** (Gemini, как в «Радаре»): автоответы на типовые вопросы и
  подсказки оператору (черновик ответа). Реализуется через тот же `radar/ai.py`
  подход; без ключа ИИ бот работает на детерминированном FAQ. Флаг `support_ai`.
- **SLA полностью**: `sla_due_at` считается при создании, автоэскалация при
  просрочке первого ответа (повышение приоритета, уведомление администрации).
- **Вложения**: скриншоты/файлы/фото принимаются как сообщение-вложение
  (`kind: attachment`), пересылаются оператору в рамках тикета.

## 6. Решения (закрытые вопросы)

1. **Формат номера.** ✅ Решено: **`#2026-123`** — с префиксом года.
2. **Группы/топики.** ✅ Решено: бот добавляется в группу, куда уже добавлен
   основной бот «Радара»; в группе включены топики — одна тема = один тикет.
   Сообщение в группе (или в топике) создаёт тикет так же, как в личке.
3. **Оценка ответа.** ✅ Решено: кнопка 👍/👎 по закрытию, с агрегацией
   статистики удовлетворённости (по операторам и категориям).
4. **ИИ.** ✅ Решено: ИИ-ассистент (Gemini) — в первую версию, за флагом
   `support_ai`; без ключа — детерминированный FAQ.
5. **SLA.** ✅ Решено: полностью сразу — дедлайн первого ответа, автоэскалация
   при просрочке, приоритеты, отчёт по SLA.
6. **Прикреплённые файлы.** ✅ Решено: принимаются (скриншоты, документы, фото)
   как вложения в тикет.

## 7. Экспорт диалога (текстовый файл)

По итогу тикета оператор (или сам клиент) получает **`.txt`** (markdown-подобный,
читается человеком). Структура:

```text
Обращение #2026-123
Тема: <subject>
Категория: <category>
Автор: @username (id 123456)
Оператор: @operator
Открыто: 2026-11-21 15:32 (MSK)
Закрыто: 2026-11-21 16:10 (MSK)

[15:32] 👤 @username: текст сообщения клиента
[15:40] 🛡 @operator: текст ответа оператора
[15:41] ⚙️ система: тикет закрыт
```

Реализация: собрать `ticket_messages` по `ticket_id` в порядке времени, отдать
как документ (`BufferedInputFile`, `send_document`). Формат — `.txt` (простота);
при желании `.md` — та же генерация с разметкой.

### 7.1 Сохранение

- **По запросу** — команда оператора `/export <номер>` или кнопка в тикете.
- **По закрытию** — файл прикладывается к сообщению о закрытии тикета.
- Файл также сохраняется в `data/exports/<номер>.txt` на диске (для архива).

## 8. Объём работы по файлам (в репозитории `radar`)

Код поддержки живёт в подкаталоге `support/` того же репозитория (решение
владельца), чтобы `install.sh` ставил оба бота одной командой.

```
support/
├── main.py                  # вход, запуск polling
├── core/
│   ├── config.py            # чтение .env (SUPPORT_BOT_TOKEN, SUPPORT_ADMIN_ID, SUPPORT_DB_FILE)
│   ├── roles.py             # иерархия ролей (порт radar/roles.py)
│   ├── classify.py          # классификация + FAQ + ИИ-подсказки
│   ├── sla.py               # дедлайны, автоэскалация
│   └── export.py            # генерация .txt диалога
├── db/
│   ├── models.py            # User, Ticket, TicketMessage
│   ├── engine.py            # async engine + session
│   └── repo.py              # create_ticket, add_message, list_tickets, …
├── handlers/
│   ├── client.py            # /start, /support, приём сообщений и вложений
│   ├── operator.py          # /queue, /open, /reply, /close, /export
│   ├── group.py             # работа в группе с топиками (одна тема = тикет)
│   └── admin.py             # назначение ролей, FAQ-редактирование, /stats
├── i18n.py                  # ru/en тексты
├── .env.example             # SUPPORT_* переменные
├── requirements.txt         # aiogram, aiohttp, sqlalchemy[asyncio], aiosqlite, python-dotenv
├── Dockerfile
└── tests/
    ├── test_tickets.py      # номера (#2026-N), доступ (только автор/модератор+), статусы, SLA
    ├── test_group.py        # топики групп
    └── test_export.py       # генерация .txt
```

Тесты — без сети: порядковые номера с префиксом года, правило доступа
(обычный пользователь не видит чужой тикет), переходы статусов, SLA-эскалация,
генерация файла диалога, разбор вложений.

## 9. Развёртывание (общий установщик, два контейнера)

Бот поддержки ставится тем же `install.sh`, что и основной «Радар» (решение
владельца): установщик поднимает **два контейнера в разных Docker**-проектах.

1. Установщик спрашивает, ставить ли бота поддержки, и запрашивает токен
   `@BotFather` для него (отдельный от основного бота).
2. Заполняются `SUPPORT_*` переменные в `.env`:
   ```bash
   SUPPORT_BOT_TOKEN=...support_token...   # другой токен, НЕ от основного бота
   SUPPORT_ADMIN_ID=<ваш id>
   SUPPORT_DB_FILE=data/support.db         # своя БД
   SUPPORT_GROUP_ID=<id группы с топиками> # куда бот добавлен
   ```
3. Контейнер `support_container` / образ `support_image` — уникальные, чтобы
   не конфликтовать с `radar_container`/`radar_image` на том же сервере.
4. Подробности монтажа двух ботов — в `docs/PLAN_6_0_0.md` (раздел про
   установщик).

## 10. Что НЕ входит в первую версию

- Внешняя капча для групп (Turnstile/hCaptcha) — не нужна, модерация в группе
  уже есть в «Радаре».
- Полная веб-панель поддержки — минимальная статистика в боте (`/stats`)
  достаточна; расширение — отдельным выпуском.
- Мультиязычность сверх ru/en (поддержка ведётся на двух языках).
- Экспорт в PDF/другие форматы — только `.txt` (по запросу и по закрытию).
