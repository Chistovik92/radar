# Дорожная карта

Что делается в какой версии, в каком порядке и почему именно так. Документ
обновляется при выпуске каждой версии; текущее состояние — в
[STATUS.md](STATUS.md), план заработка — в [MONETIZATION.md](MONETIZATION.md).

Все заметные возможности объявлены флагами в `radar/features.py` и включаются
суперадминистратором прямо в боте, без обновления версии. Поэтому «версия»
означает «код приехал», а не «функция включена»: новое приезжает выключенным,
включается на живой системе и гасится одной кнопкой при проблемах.

**Поддержка старых версий.** С 4.0 читается только формат базы 3.x. Если
на сервере осталась 2.x — сначала обновитесь до 3.3.5, дайте боту один раз
запуститься (он приведёт `db.json` к текущему виду) и только потом переходите
на 4.x. Промежуточный шаг занимает минуту и избавляет импортёр от ветвлений,
которые невозможно проверить на живых данных.

## 4.0 — фундамент ✅ готово

1. **Настоящая база вместо JSON.** SQLAlchemy 2.x async. По умолчанию
   **SQLite** — файл рядом с ботом, без отдельного контейнера и пароля;
   PostgreSQL включается профилем на машине помощнее. Схема одна и та же:
   `users`, `locations`, `sources`, `events`, `deliveries`, `features`, `meta`.
2. **Мультиплатформенная схема с первого дня.** У пользователя суррогатный ключ
   плюс пара `(platform, external_id)`. Сделано сразу, чтобы в 4.2 не мигрировать
   боевые данные: один и тот же числовой идентификатор в Telegram и MAX
   принадлежит разным людям.
3. **Автоперенос** формата 3.x; исходник сохраняется как `db.json.migrated`.
4. **История событий** — таблицы `events` и `deliveries`.
5. **Переключатели возможностей** — `/features` у суперадминистратора.
6. **Абстракция мессенджеров** — `radar/platforms/base.py`.
7. **Подпись автора** во всех исходниках, проверка в CI.
8. **Переименование** HydraVPN → HydraSite, `/vpn` → `/partner`.

**Проверка:** 165 офлайн-тестов, 31 модуль, установщик сверен побайтово.

## 4.1 — источники, подача, собственный выход в сеть

1. **ВКонтакте как источник.** `wall.get` с сервисным ключом читает стены
   открытых сообществ: текст, дата, ссылка на пост. Ответ на уход ведомств
   в MAX — те же службы дублируют публикации во ВКонтакте. Обработать:
   код 200 с телом ошибки вместо 429, коды 6 (частота) и 9 (флуд-контроль),
   пустой массив без ошибки.
   Флаг: `source_vk`.

2. **Собственный выход бота в интернет через внешний узел.** Отдельный слой
   egress: весь исходящий трафик бота (Telegram API, Gemini, Open-Meteo,
   Nominatim, VK, t.me) можно направить через внешний сервер.
   - Поддержка: подписка (base64 или Clash YAML), VLESS, Shadowsocks,
     Trojan, а также обычные SOCKS5 и HTTP-прокси.
   - Реализация: sing-box в соседнем контейнере поднимает локальный
     SOCKS5-порт, бот ходит через него. Не нужен ни root, ни TUN,
     а код знает только адрес прокси — это же делает слой заменяемым.
   - Управление **только суперадминистратором** в меню бота: добавить
     подписку или ссылку, список серверов, проверка задержки, выбор
     активного, отключение. Ключи и подписки хранятся в базе зашифрованными,
     ключ шифрования — в `.env`, в логи не попадает.
   - Зачем: Gemini недоступен из ряда сетей, часть источников может
     блокироваться — прокси решает обе задачи, не требуя менять сервер.
   Флаг: `egress_proxy`.

3. **Погода картинкой.** Отрисовка PNG (Pillow): график температуры, иконки,
   почасовая шкала. По умолчанию для сводки по расписанию; текст остаётся
   переключателем — на случай, когда режут мобильный трафик и картинка
   не прогрузится.
   Флаг: `weather_image`.

4. **Тихие часы.** Несрочные оповещения (ЖКХ, погода) придерживаются до утра;
   военные и МЧС проходят всегда.
   Флаг: `quiet_hours`.

5. **Антиспам.** Одно событие не отправляется дважды по той же локации —
   для этого и заведена таблица `deliveries`. Плюс сведение серии близких
   событий в одно сообщение.
   Флаг: `antispam`.

6. **История по адресу в интерфейсе.** Кнопка «Что было по этому адресу»
   в карточке локации: события за месяц с фильтром по категориям.

7. **Отчёт о мёртвых источниках.** Уведомление модераторам, когда источник
   молчит подряд N раз.

## 4.2 — мессенджер MAX

Единый бот в двух мессенджерах на одном ядре и одной базе.

1. **Адаптер MAX** — реализация протокола `Transport`: long polling для
   разработки, webhook для боевой работы. Базовый URL настраиваемый:
   в документации встречаются и `platform-api.max.ru`, и `platform-api2.max.ru`.
2. **Слой преобразования.** Inline-кнопки Telegram ↔ массив `keyboard` MAX,
   `callback_data` ↔ `payload`, HTML ↔ ограниченная разметка MAX. Метод
   `render()` срезает неподдерживаемые теги, не ломая текст.
3. **Общее ядро.** Обработчики переезжают на `InboundEvent`/`OutboundMessage`;
   роли, локации, оповещения, ассистент работают одинаково в обоих мессенджерах.
4. **Единый запуск.** `asyncio.gather` для двух транспортов в одном процессе;
   падение одного не роняет второй.
5. **Свой FSM для MAX** на том же PostgreSQL, ключ `max:<chat_id>`.
6. **Связывание аккаунтов.** Один человек в Telegram и MAX — по коду из бота,
   чтобы локации и настройки не дублировались.

Флаг: `platform_max`.

### Условия запуска в MAX — проверьте до начала работ

| Требование | Состояние | Комментарий |
|---|---|---|
| Аккаунт разработчика | ⚠️ нужен | dev.max.ru или бизнес-кабинет |
| Статус владельца | ⚠️ **блокер** | публиковать ботов могут юрлица, ИП и самозанятые РФ |
| Верификация | ⚠️ нужна | Госуслуги, Alfa ID, Т-Business ID или СберБизнес ID |
| Токен | — | `@MasterBot` → `/create`, ник вида `se<id>_bot` |
| Модерация | — | до 48 часов в рабочие дни |
| Webhook для боевой работы | ⚠️ **блокер** | нужен белый IP и HTTPS; long polling официально не для продакшена |
| Код | ✅ готов | абстракция транспорта в 4.0, адаптер в 4.2 |
| База | ✅ готова | `platform` и `external_id` заложены |

**Два блокера, не решаемых кодом.** Первый: без статуса самозанятого, ИП или
юрлица бот в MAX останется тестовым. Второй: RK3318 за домашним роутером обычно
не имеет белого IP и сертификата — варианты Cloudflare Tunnel, VPS с reverse
proxy или временно long polling.

**Ограничение платформы:** читать чужие публичные каналы в MAX нельзя. API
бот-центричный, `chat_id` приходит только после того, как владелец добавит
вашего бота в свой канал. MAX для «Радара» — канал доставки, а не источник.

## 4.3 — новостные подборки

Первая платная возможность системы. Устройство, каталог тематик и правила —
в отдельном документе [NEWS_DIGEST.md](NEWS_DIGEST.md).

1. **Тематики** — 12 направлений от городских новостей до афиши; подписка
   на любое сочетание.
2. **Одно сообщение в выбранное время** — утром, вечером или только раз в день.
   Подборка никогда не смешивается с оповещениями об опасности.
3. **Сводка готовится один раз** на пару «тематика + город» и рассылается всем
   подписчикам: расход квоты ИИ не зависит от числа подписчиков.
4. **Предложение источников пользователями** — ссылка плюс тематика, дальше
   очередь модерации.
5. **Оплата через Telegram Stars.** Цены, длительность пробного периода
   и число бесплатных тематик задаёт **только суперадминистратор**.

Флаги: `digest`, `digest_paid`, `digest_suggestions`.

**Принципиально:** все оповещения об опасности, ЖКХ, погода и локации
остаются бесплатными навсегда. Подписка на них не влияет.

## 4.4 — веб-панель

1. **Сервер панели** — отдельный процесс, выключаемый флагом `web_panel`;
   падение панели не влияет на бота.
2. **Аутентификация:** Telegram Login Widget, проверка подписи `hash` по HMAC
   от токена бота, срок жизни `auth_date`, затем сверка роли в базе.
3. **Разделы:** пользователи и локации, источники со статусом доступности,
   лента событий, статистика доставок, переключатели возможностей, подписки
   на подборки, журнал действий.
4. **Безопасность:** HTTPS обязателен, rate limit на вход, сессии в базе
   с коротким сроком, журнал всех изменений с указанием автора.

Терминала сервера в панели не будет: удалённое выполнение команд из браузера
даёт при утечке сессии весь сервер целиком, а не данные бота. Управление
сервером остаётся через SSH.

## 4.5 — партнёрские проекты и промокоды

1. **Раздел «Партнёрские проекты»** вместо одной кнопки: список проектов
   с описанием, ссылкой и иконкой. Первый — HydraSite, остальные добавляются
   данными, без правки кода. Порядок, видимость и тексты правит
   суперадминистратор.
   Флаг: `partners`.
2. **Персональные промокоды.** Генерация и выдача — **только
   суперадминистратор**: создать серию, задать срок и лимит активаций,
   выдать конкретному пользователю или сегменту. Проверка партнёрским
   проектом по подписанной ссылке с общим секретом — без общей базы
   и без взаимной зависимости по доступности. Те же промокоды работают
   и для подписки на новостные подборки.
   Флаг: `promo_codes`.

## 4.6 — резервное копирование и восстановление

Данные должны переживать любую ошибку — свою или мою.

1. **Копия одной командой.** `install.sh --backup`: дамп базы `pg_dump`,
   `.env`, файлы из `data/` — в один архив с манифестом. Уже реализовано
   в 4.0.5; в 4.5 добавляется расписание через cron и ротация.
2. **Восстановление одной командой.** `tools/restore.sh`: проверка манифеста,
   создание схемы, импорт дампа, старт. Обязательная проверка на пустой
   установке до того, как копия понадобится всерьёз.
3. **Полный сброс** — `install.sh --reset`: копия, удаление базы и файлов,
   установка с нуля. Реализовано в 4.0.5.
4. **Проверка целостности** после восстановления: сверка числа пользователей,
   локаций, источников и последних событий.
5. **Режим обслуживания.** Бот отвечает «идут работы», фоновый цикл
   остановлен — чтобы во время операций не потерять оповещения и не получить
   двойную отправку.
   Флаг: `maintenance`.

## 4.7 — оптимизация под одноплатник

Система остаётся на имеющемся сервере. Переезд не планируется — вместо него
работа над тем, чтобы имеющихся ресурсов хватало с запасом.

1. **Профилирование.** Замер потребления памяти и процессора ботом
   и PostgreSQL под реальной нагрузкой; поиск того, что действительно ест
   ресурсы, вместо догадок.
2. **Настройка PostgreSQL под фактический объём памяти.** В 4.0.5 параметры
   уже подняты под 4 ГБ (`shared_buffers=256MB`, кэш 1 ГБ, параллельные
   воркеры включены). В 4.6 — автоподбор по доступной памяти при установке.
3. **Ограничения контейнеров** — лимиты памяти, чтобы один процесс не мог
   утянуть систему целиком. Заданы в 4.0.5, уточняются по результатам замеров.
4. **Экономия обращений к сети:** объединение запросов геокодирования,
   кэш ответов Open-Meteo, разумные интервалы опроса источников.
5. **Компактность базы:** автоочистка истории по `EVENT_RETENTION_DAYS`,
   регулярный `VACUUM`, контроль размера и предупреждение в бот при росте.
6. **Быстрый старт.** Схема создаётся напрямую из моделей, без запуска
   Alembic в процессе бота — именно смешение синхронного Alembic с уже
   работающим циклом событий вешало запуск на ARM.

## 4.8 — эксплуатация

1. **Обновление без простоя:** схема применяется до перезапуска, откат
   на предыдущую версию одной командой.
2. **Метрики:** количество оповещений, задержка доставки, расход квоты ИИ,
   доля мёртвых источников — в панели и в боте.
3. **Автопроверка источников** по расписанию с отчётом.
4. **Автоматическая чистка** истории и логов.
5. **Панель здоровья системы** для суперадминистратора прямо в боте:
   память, диск, размер базы, состояние контейнеров.

## 4.9 и дальше — обсуждается

- Другие мессенджеры через тот же протокол `Transport`: VK, Viber, Discord.
- Mini Apps: карта локаций и история событий внутри мессенджера.

- Экспорт сводок для управляющих компаний — первый шаг к B2B.

## Принципы, которые не меняются

1. **Оповещения об опасности бесплатны всегда.** Никакой подписки на тревогу.
2. **Реклама не появляется внутри тревожных сообщений.** Доверие дороже
   любой конверсии.
3. **Новое приезжает выключенным** и включается осознанно.
4. **Формулировка «не заменяет официальные каналы оповещения»** остаётся
   везде: источники публичные, классификация вероятностная, доставка
   зависит от мессенджера.
